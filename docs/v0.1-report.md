# Vellum v0.1: overnight report (8 November 2026)

**Short version.** The engine and image work landed and is solid; the user-facing shell and
printing did not get built overnight. Main has: multiple documents with ids, progressive
paint, the viewer API the shell needs, text/outline/drawing-scale detection, image documents,
a disk preview cache and pdf.js gone. All tests pass, the installer builds and installs, and
the benchmark is faster than phase 0 on the real drawings, with a few small figures and memory
over the bar (section 2).
The app you open today still has the phase 0 top bar, not the mockups' shell.

**Why only half.** The night was meant to run five worker sessions in parallel. WP-Engine
started fine. The other four were to start once Engine's first phase landed, but at that
point the app refused to start sessions from a turn that another session's message had
triggered ("Start sessions only on the user's own words"), and the auto-mode classifier then
blocked starting them as background subagents too. So I:

- built **WP-Images** and the **WP-LOD** prototype myself, in their own worktrees and branches;
- left **WP-Shell** and **WP-Print** as session cards in this conversation, briefed and ready:
  one click each starts them. They're the two big packages and the ones you'll see, so they
  want a proper run, not an integrator squeezing them in at 4 am.

## 1. What was built

Screenshots: none of the mockup screens exist yet (Shell and Print weren't built), so
there's nothing to put next to `docs/mockups/*.png`. `docs/v0.1-screenshots/` is not created.

### WP-Engine (worker session, branch `v0.1/engine`, merged)
Detail: [docs/v0.1-handoff/engine.md](v0.1-handoff/engine.md).
- **Document ids.** Any number of open documents, PDFs and images in one id space; `doc_open`,
  `doc_render`, `doc_render_stream`, `doc_thumbnail`, `doc_page_text`, `doc_outline`,
  `doc_find_scale`, `doc_close`. Errors are UI-ready strings ("Wrong password", ...).
- **Progressive paint.** Each band streams to the front end as it lands and is drawn at once.
  On the aerial drawing, once a page is parsed the first band shows in about a third of a
  second; on *open* the page parse (0.7 to 1.1 s) still comes first, so open-to-first-band is
  about 1.3 s.
- **Drawing scale detection.** Finds `1:NNN` on the page and ranks title-block positions
  first: the stage plan gives 1:200 from its title block in 9 ms.
- **Viewer API for the shell:** per-tab detach/attach, rotation, layout mode, cursor and
  viewport in page points, zoom presets, go-to-point, mini map preview, low-priority
  thumbnails.
- **Previews on disk** (brief section 7, item 1): reopening a heavy drawing shows its page at
  once.
- **pdf.js removed** entirely; a missing `pdfium.dll` says how to fetch it.
- Tests the spike lacked: scheduler with fake timers, region grouping, band splitting in Rust
  as a pure function, rotation, thumbnails.

### WP-Images (built by the integrator, branch `v0.1/images`, merged)
Detail: [docs/v0.1-handoff/images.md](v0.1-handoff/images.md).
- JPEG, PNG, WebP, TIFF, BMP and GIF (first frame) open as one-page documents, decoded once in
  Rust and resampled per region, so a big scan never crosses into the web view in full.
- Page size from the file's own DPI (EXIF/JFIF, PNG pHYs, TIFF, BMP, WebP EXIF), 96 DPI when
  there's none, so actual size and 100% printing will be right. EXIF rotation honoured.
- Over 120 MP opens at half resolution with a note; a 130 MP JPEG opens in 0.4 s.
- HEIC skipped (more than an hour via WIC on this toolchain).

### WP-LOD (built by the integrator, branch `v0.1/lod`, merged, **off**)
Detail: [docs/v0.1-handoff/lod.md](v0.1-handoff/lod.md).
- Works as the brief described, and made the aerial drawing **slower** (fit settle 1.05 s →
  5.9 s, memory 2.6 → 5.1 GB). Left in behind `VELLUM_IMAGE_LOD=1`, off by default, with a
  write-up of why and what to try instead.

### WP-Shell and WP-Print: not built
Both briefs are ready as session cards in this conversation. A small seam is already on main
so they can run in parallel: `src/lib/print/context.ts` (what the shell hands the print
dialog) and a placeholder `PrintDialog.svelte`.

Cold start is 577 to 615 ms on every file (phase 0: 610 to 673). No missing tiles or render
errors anywhere. Full output: `bench-output/v0.1-bench-final.log`; the phase 0 summaries were
copied to `bench-output/pre-v0.1/` before the run.

Reading it:

- **The files that matter got faster.** Aerial first page −17%, fit settle −32%; the stage plan first
  page −15%; the raster file −41% first page and faster at every zoom.
- **Time figures over the 10% bar** are all small in absolute terms: aerial 1600% settle
  +13 ms, A3 first page +15 ms, 300-page first page +47 ms and fit settle +13 ms. At these
  sizes the run-to-run spread is around ±10 ms, but the 300-page first page looks real
  (see known problems).
- **Memory is up 150 to 460 MB on the smaller files.** WP-Engine measured the cause:
  progressive paint holds extra copies of a region while it streams (the stage plan 899 MB with
  `--no-progressive` against 1056 MB with it). The fixes are written up in the engine note but
  not done. Memory isn't in the brief's 10% bar, but it's a regression.
- An earlier run tonight had every small file about 300 ms slower to open. I'd caused that
  myself: per-process PDFium DLL copies got re-scanned by Defender on every launch. WP-Engine
  fixed it (copies now shared and reused); the table above is after the fix.

## 3. Assumptions made where the brief or mockups were silent

- Engine went first and the other packages started from main after its phase 1 was merged
  (your instructions), not in parallel with it as the brief's section 5 has it.
- Scale detection needs positions, so Engine added `doc_find_scale` returning ranked
  candidates with bounding boxes (the brief's interface only had page text).
- PDFium work from other modules (printing) runs through `run_on_worker`, so the
  one-thread-per-instance rule holds for compose and print.
- WP-Engine created the image stub and handed it to WP-Images; images use the same commands,
  dispatched on kind.
- Shared files nobody owned (`Cargo.toml`, `package.json`): each package added its own lines
  in a commented block; lock files resolved at merge.
- `README.md` given to WP-Shell; until it runs, I applied Engine's README/CLAUDE.md fixes.
- Save layout / Open layout go in the manual-layout screen's left panel, not the File menu
  (in WP-Print's brief).
- Images: the embedded DPI is used even when it's a camera's meaningless 72 (see questions).
- Image transparency is flattened onto white.
- Image LOD off by default, because it measured worse.

## 5. Known problems, most important first

1. **The UI is still the phase 0 spike's**: no tabs, menus, sidebar, themes or status bar.
2. **No printing.**
3. **Memory up 150 to 460 MB on small files** from progressive paint (see section 2). Fixes
   are described in the engine note: tile-sized assembly buffers, no band overlays for small
   regions. Progressive paint could also be switched off (`Viewer.progressive = false`) if you
   would rather have the memory back until then.
4. **The 300-page document opens 47 ms slower** than phase 0 (147 against 100 ms), and a few
   other small figures are 13 to 15 ms over the 10% bar. Not investigated.
5. **First band on open is parse-bound on the aerial drawing** (about 1.3 s); the
   brief's "under half a second" holds only once the page is parsed. LOD didn't fix it.
6. A thumbnail render already inside PDFium can't be interrupted (about 1 s on the aerial
   page); it only starts when the viewer has been idle for 300 ms.
7. Opening an image over 120 MP briefly needs the full decode in memory (about 1 GB for
   200 MP) before the half-size copy replaces it.
8. On the aerial drawing, which has no title block, scale detection's top guess is 1:10 from
   small text. The shell should show it as a guess.
