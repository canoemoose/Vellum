# Vellum v0.1: report (8 November 2026, updated in the afternoon)

**Short version.** All five packages are now on main. Overnight, Engine, Images and the LOD
prototype landed; this morning WP-Shell and WP-Print ran as their own sessions and were
merged, along with an engine fix that the print work turned up (a title block's "1:200 @A3"
on an A1 page is now read as 1:100). All tests pass (273 Vitest, 119 Rust, svelte-check
clean), the release exe opens the test drawings with no render errors, and the installer
builds. Three new heavy PDFs were benchmarked: two are as quick as the stage plan, and one
(Bayou Towers) takes about 5 s per render because of a single image that PDFium decodes very
slowly and never caches. A measured fix is written up in
[v0.1-heavy-pdfs.md](v0.1-heavy-pdfs.md).

Nobody has looked at the screen yet: the shell and print dialog are checked by their tests,
by their workers' DevTools-driven runs and screenshots, and by smoke runs, not by eye.

**How the night went.** The plan was five worker sessions in parallel. WP-Engine started
fine; the other four were to start once Engine's first phase landed, but the app refused to
start sessions from a turn another session's message had triggered, and the auto-mode
classifier blocked background subagents too. So I built WP-Images and WP-LOD myself and left
Shell and Print as session cards, which you started this morning.

## 1. What was built

Screenshots (captured by the workers from the running exe): `docs/v0.1-screenshots/`
`shell-dark.png`, `shell-light.png`, `print.png`, `print-manual.png`, next to the mockups in
`docs/mockups/`.

### WP-Engine (worker session, branch `v0.1/engine`, merged)
Detail: [docs/v0.1-handoff/engine.md](v0.1-handoff/engine.md).
- **Document ids.** Any number of open documents, PDFs and images in one id space; `doc_open`,
  `doc_render`, `doc_render_stream`, `doc_thumbnail`, `doc_page_text`, `doc_outline`,
  `doc_find_scale`, `doc_close`. Errors are UI-ready strings ("Wrong password", ...).
- **Progressive paint.** Each band streams to the front end as it lands and is drawn at once.
  On the aerial drawing, once a page is parsed the first band shows in about a third of a
  second; on *open* the page parse (0.7 to 1.1 s) still comes first, so open-to-first-band is
  about 1.3 s.
- **Drawing scale detection.** Finds `1:NNN` on the page and ranks title-block positions
  first. Since this morning, a ratio followed by "@A3", "@ A3" or "at A3" is converted to the
  page's own size: the stage plan (A1, "1:200 @A3") now reports 1:100, keeping the written
  1:200 as `statedRatio` (`67ca423`, 6 new tests).
- **Viewer API for the shell:** per-tab detach/attach, rotation, layout mode, cursor and
  viewport in page points, zoom presets, go-to-point, mini map preview, low-priority
  thumbnails.
- **Previews on disk**: reopening a heavy drawing shows its page at once.
- **pdf.js removed** entirely; a missing `pdfium.dll` says how to fetch it.

### WP-Images (built by the integrator, branch `v0.1/images`, merged)
Detail: [docs/v0.1-handoff/images.md](v0.1-handoff/images.md).
- JPEG, PNG, WebP, TIFF, BMP and GIF (first frame) open as one-page documents, decoded once in
  Rust and resampled per region.
- Page size from the file's own DPI, 96 DPI when there's none. EXIF rotation honoured.
- Over 120 MP opens at half resolution with a note; a 130 MP JPEG opens in 0.4 s.
- HEIC skipped.

### WP-LOD (built by the integrator, branch `v0.1/lod`, merged, **off**)
Detail: [docs/v0.1-handoff/lod.md](v0.1-handoff/lod.md).
- Made the aerial drawing **slower**, so it's behind `VELLUM_IMAGE_LOD=1`. This afternoon it
  turned out to be the right mechanism for a different file: see the heavy PDFs note.

### WP-Shell (worker session, branch `v0.1/shell`, merged)
Detail: [docs/v0.1-handoff/shell.md](v0.1-handoff/shell.md).
- The mockups' shell: custom title bar with tabs, menus, toolbar, sidebar (pages, outline),
  mini map, status bar (cursor position, paper size, drawing scale), dialogs, light and dark
  themes with accent colours, settings.
- One viewer shared by many tabs (detach/attach), so switching tabs is instant.
- Single instance: a second launch hands its file to the running window.
- Window size and position restored, clamped on screen.
- Installer registers Vellum under "Open with" for PDFs and images, without becoming the
  default.
- Explorer drops are ignored while the print dialog is open (asked for by WP-Print).

### WP-Print (worker session, branch `v0.1/print`, merged)
Detail: [docs/v0.1-handoff/print.md](v0.1-handoff/print.md).
- Print dialog: Fit, To scale (1:N from the drawing scale), Tile with overlap and cut marks,
  margin stamp, colour modes, presets, preview with sheet navigation.
- Manual layout screen: place pages and images on sheets, move, scale, crop, auto-arrange,
  Save as PDF, Save/Open layout.
- Output: jobs composed into a PDF with PDFium (vectors stay vectors), then printed through
  GDI as 300/600 dpi bands, or Vector. Default is Image 600 dpi; Vector is offered.
- Checked through Microsoft Print to PDF to the millimetre: the stage plan at Fit on A3, the stage plan at 1:200
  on A3 (with the scale set to 1:100), the aerial drawing tiled onto 13 A3 sheets, and a
  manual sheet with two pages and a JPEG.

- **Bayou Towers is the evil one.** Page 1 is one 24 MP colour JPEG that PDFium takes about
  4.15 s to decode, on every render, at every zoom, on every worker. The JPEG data itself
  decodes in 59 ms at ⅛ size outside PDFium, so the cost is PDFium's own image path (most
  likely its colour-space conversion). Decoding it once and swapping a plain bitmap in, the
  LOD prototype's mechanism, measured **3 ms** at fit (from 4,160) and **14 ms** per 400%
  tile (from 1,464).
- **Main is 5 to 25% slower than the overnight build on most settle figures.** The render
  code differs by one field, so it's the bigger front end or run order (the overnight build
  ran first). Needs an alternating re-run before believing it.

## 3. Assumptions made where the brief or mockups were silent

- Engine went first and the other packages started from main after its phase 1 was merged
  (your instructions), not in parallel with it as the brief's section 5 has it.
- Scale detection needs positions, so Engine added `doc_find_scale` returning ranked
  candidates with bounding boxes (the brief's interface only had page text).
- A scale written for another sheet size ("1:200 @A3") is converted to the page's own size;
  the shell shows the converted figure.
- PDFium work from other modules (printing) runs through `run_on_worker`, so the
  one-thread-per-instance rule holds for compose and print.
- Shared files nobody owned (`Cargo.toml`, `lib.rs`'s command list, `package.json`): each
  package added its own lines in a commented block; conflicts resolved as the union at merge.
  `dialog:allow-save` added to the capabilities at merge for Print's save dialogs.
- Print defaults to Image 600 dpi; Vector is offered in Advanced, because it's unverified on
  real printer drivers.
- Images: the embedded DPI is used even when it's a camera's meaningless 72 (see questions).
- Image LOD off by default, because it measured worse on the aerial drawing.
- Each package's own assumptions are listed in its hand-over note.

## 5. Known problems, most important first

1. **Bayou Towers-style images take about 4 s per render** (section 2). Fix measured, not
   built; see the heavy PDFs note.
2. **Memory up 150 to 460 MB on small files** from progressive paint. Fixes are in the engine
   note. Progressive paint can be switched off (`Viewer.progressive = false`) meanwhile.
3. **Print composition blocks one PDFium worker** while it runs (about 20 s for the aerial
   drawing tiled onto 13 sheets), so part of the viewer stops rendering during it.
4. **Scale boxes on the aerial drawing lie outside its page** (x up to 13,300 pt on a 745 pt
   page). The shell ignores tiny text, so it shows "Scale not set", but the engine's text
   coordinates for that page look wrong.
5. **First band on open is parse-bound on the aerial drawing** (about 1.3 s).
6. **The 300-page document opens 47 ms slower** than phase 0. Not investigated.
7. **Two copies of Vellum with different WebView2 settings can't run at once**: the second
   fails to start (0x8007139F). Normal launches go to the running window instead, so users
   won't see it; it bit the workers' testing. One benchmark run also hung for 15 minutes
   this afternoon while other copies were running; the rerun was clean.
8. Tiled output through Microsoft Print to PDF is large (102 MB for 13 aerial tiles) because
   it's raster; Save as PDF is vector and small.
9. Opening an image over 120 MP briefly needs the full decode in memory (about 1 GB for 200 MP).
10. No Windows 11 snap layouts on hovering maximise (custom title bar, as the brief accepted).
