# Heavy PDFs: benchmark and speed-up ideas (8 November 2026)

Three new files in `test-files/` (not in git), benchmarked with the other two real drawings
against the overnight v0.1 build, then profiled where they were slow.

## The files

| File | Size | What's in it |
|---|---:|---|
| `3397 Drawings MMA Curtis Hall_Sec 1.pdf` | 45 MB | 720 small images; vector sheets |
| `BayouTowersFullDrawingSet_dwgs_1_13.pdf` | 65 MB | 13 scanned sheets: page 1 is one 6144 × 3976 colour JPEG (24 MP) with its own colour space object; pages 2 to 13 are 12000 × 15200 1-bit JBIG2 scans (182 MP each) |
| `sample-50-MB-pdf-file.pdf` | 52 MB | Two big images, one with a soft mask |

Pan is 57 to 60 fps everywhere in both builds; cold start 582 to 672 ms; no render errors or
missing tiles. Raw output: `%TEMP%\vellum-smoke\out-base` and `out-now` on this machine.

Reading it:

- **Curtis Hall and the 50 MB sample are fine**: as quick as the stage plan. Size isn't the
  problem; one kind of image is.
- **Bayou Towers is the evil one**: about 5 s before anything shows and 4 to 5 s to sharpen at
  fit. Everything below is about that file.
- **Now is 5 to 25% slower than the baseline on most settle figures.** The render code
  between the two builds differs by one field (the scale fix), so it's the front end (Shell
  is a much bigger app around the same canvas) or run order: baseline ran first, then now,
  on a machine that had been busy. Not chased yet; the next step is a 5-run, alternating
  re-run before believing it.

## Why Bayou is slow

With `VELLUM_PDFIUM_TIMING=1`:

- **Every render of page 1 costs about 4.15 s**, at any zoom, every time, on any worker.
  Rerun with one PDFium thread: still 4.15 s every time. PDFium does not keep this image
  decoded between renders.
- A 400% tile costs 0.75 to 1.5 s, more the further down the page it is: PDFium decodes the
  image from the top down to the tile's bottom edge for every tile.
- Pages 2 to 13 (JBIG2) cost about 0.7 s for the first render and then about 25 ms, so
  PDFium does cache those. With 8 workers, each worker pays the 0.7 s once.
- The JPEG data itself is not slow: the LOD prototype decodes it at ⅛ size in 59 ms. The 4 s
  is PDFium's own image pipeline, most likely converting through the image's colour space
  object (the object sits inside a compressed object stream, so I didn't confirm its type).

A throwaway probe (not committed) decoded page 1's image once with
`FPDFImageObj_GetBitmap` and swapped a plain bitmap into a second handle of the page, the
mechanism the LOD prototype already uses:

| Step | Time |
|---|---:|
| Fit render today | 4,160 ms (every time) |
| One-off decode of the image | 4,076 ms |
| Make a ⅛ greyscale-averaged copy | 8 ms |
| Fit render with the ⅛ copy swapped in | **3 ms** |
| 400% tile today | 1,464 ms |
| 400% tile with the full decoded bitmap swapped in | **14 ms** |
| Fit render with the full decoded bitmap swapped in | 37 ms |

*10 Nov follow-up:* Bayou's 4 s turned out to be the image's ICC profile (a 188 KB scanner
profile), not the JPEG; idea 2 is built with our own ICC conversion
([bayou-image-scope.md](bayou-image-scope.md)). The aerial drawing ("Aerial" above,
`projectlayoutmarch2021.pdf`) was probed too: its cost is 327,000 vector and text objects,
not its 1 MP JPEG tiles, so none of the image ideas below help it
([speed-handoff.md](speed-handoff.md), idea 2a).

## Ideas, best first

1. **Decode expensive images once and keep them** (measured above: 4 s → 3 ms at fit, 1.5 s
   → 14 ms per deep tile). Generalise the LOD prototype from "big JPEGs" to "any image that
   proved slow": when a page's render takes over, say, 500 ms and the page has a large image,
   decode that image once on a background worker, keep the full bitmap plus a ½ / ¼ / ⅛
   pyramid in the process-wide cache LOD already has, and swap the right level into each
   worker's second page handle. Costs: memory (page 1 is 73 MB decoded; per-worker copies
   multiply that, so see idea 3) and the first render still pays the slow decode once.
2. **Skip PDFium's slow decode for JPEGs entirely.** For a DCTDecode image, decode it
   ourselves (at ⅛, ¼ or full size with DCT scaling, as LOD does in 59 ms at ⅛), convert
   the colour space once, and swap it in. That makes even the *first* paint fast: a ¼ decode
   should cover fit zoom on this page in roughly 100 to 200 ms instead of 4.5 s. The LOD
   prototype already does the ⅛ decode for this exact page; it went unused only because a
   ⅛ copy is too coarse at fit (it kicks in below 35% render scale, fit is 65%). Adding ¼
   and ½ levels is the smallest change that would show a win on Bayou. Needs care for
   colour spaces (ICC, Indexed, CMYK, Decode arrays); where we can't reproduce PDFium's
   colour exactly, fall back to idea 1.
3. **Page affinity in the render scheduler.** Send a page's renders to the worker that
   rendered it last when it's free. PDFium's per-instance caches (parsed page, decoded
   JBIG2) then get reused: today each of 8 workers pays Bayou's 0.7 s JBIG2 decode, and the
   aerial drawing's page parse, separately. This also keeps the memory of ideas 1 and 2 to
   one or two copies.
4. **Pre-warm the neighbours.** When a page turns out slow, decode the next page's images
   in the background while the user looks at this one. Bayou is a 13-sheet set; paging
   through it is the natural thing to do.
5. *(11 Nov: a page now renders as one band only when it has an image swap or an image slow
   to decode, not for a large image as such; Bayou's cover still does, because it's swapped.)*
   **Bands for big-image pages.** Today a page with a large image renders as one band ("page
   1 has a large image: 1 band"), so nothing shows for 4.5 s. With idea 1 or 2 in place,
   banding becomes cheap again and progressive paint would work on these pages too.
6. **Check the front-end settle gap** (the 5 to 25% above) with an alternating 5-run bench
   before changing anything; if it's real, profile the web view during a settle in the bench
   window.

My recommendation: 2 then 3. Idea 2 attacks the actual cause (PDFium's JPEG path), reuses
code that already exists and is tested, and fixes first paint as well as re-renders; 3 is a
small scheduler change that helps every heavy file. Idea 1 is the safety net for images that
idea 2 can't handle.
